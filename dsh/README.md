# 《东方学刊》审稿智能体

一个可以在网页中驱动运转的中文学术期刊审稿智能体，针对《东方学刊》的编辑体例与一审惯例而建。

本包是交给下一位开发者接续开发的版本：只含应用代码、最小可跑样例与体例规范，原项目的历史优化路线图、逐文件资产账本和内部执行日志均未随包提供。验收口径见包根目录 [`docs/验收目标.md`](../docs/验收目标.md)。

**四项核心能力**：导入 `.docx` → 左右对照预览修改前后 → 格式体例审阅 → 内容错误（语法、语病、词汇、逻辑、引文、事实）审阅。

审阅结果**流式逐条呈现**：批注从标题开始，按正文、脚注、尾注的顺序一条条出现，不必等整篇跑完。

句式、语序、成分残缺等句级意见，正文标记覆盖完整句子（含句末标点与收尾引号）；词语和标点意见仍标出相应片段。原始证据片段与自动修改范围保持独立，修改后先按已保存的版本和修改记录重新定位，再计算批注显示范围。流式结果与完成结果共用这套范围处理。导出 Word 目前仍使用正文整段批注，准确的来源字符范围在导出记录中单独保留。

复核按文本量合批，每批最多12条、约6000字描述，完整原文与改法不会被截断；漏回的结论单独补问，后续重试按4条小批处理。批量保存与恢复时限制同时发布的结果数量，减少共享任务记录的争用。历史上的对照验证记录未随包提供。

## 快速开始

```powershell
cd dsh
npm start
# 打开 http://127.0.0.1:3210
```

页面操作：**导入稿件** → **开始审阅**（批阅视图里看批注逐条出现）→ 左栏看问题清单、主区看批注/原文/对比 → **导出报告**。

自动修改会写入真实 DOCX 工作版本，预览、刷新恢复和导出共用该版本。“导出当前修改稿”下载工作稿；“导出批注 Word”在工作稿上添加批注。上传原稿与每次保存的版本保存在 `data/working-versions/`，带文件哈希、父版本及逐处修改记录。部分归并修改不会显示为全部完成；位置不符、修订、域或跨链接等不支持范围明确拒改。

“撤销修改/重做修改”按一次保存恢复完整 Word 快照，一次保存可包含多处修改。修改历史、审阅记录及重复请求回执原子保存在 `data/sessions/`，刷新、内存缓存淘汰或服务重启后可恢复。新版恢复先核对任务执行者：已有待发布结果继续提交，确认执行者已退出且没有结果时登记中断；旧运行身份无法确认时显示待核对状态。历史审阅记录保留。

稿件队列、当前查看稿件保存在 `data/workspaces/`。上传先在 `data/ingestions/` 保存工作台与操作身份、登记待接收项，再保存原始文件、工作版本和会话，最后确认队列可用。断线重试沿用原身份；已完整保存原文件的任务可点“继续保存”，文件未完整收到须“重新选择文件”。未完成或失败项保留独立记录。

新版同步、异步和流式审阅共用 `data/jobs/` 中的任务、运行身份、执行租约和待发布结果。页面观察服务器进度，断线或关闭页面后任务仍可执行；重复操作沿用原任务。暂停阻止后续稿件开始，当前稿继续完成；取消请求保存后投递到执行者。结果先落盘，再核对会话提交凭证，最后登记完成。工作台列表读取一次一致的任务快照和会话元数据，查看其他稿件保持当前选择。完整浏览器流程、逐处范围及语义质量仍须分别验收。

人工决定绑定稿件、工作版本和完成审阅运行；圈画绑定版本与明确字符范围，保存确认后才显示。重审保留同版本圈画并隔离旧决定，修改版本后旧记录保留在历史中；切稿立即关闭旧详情。软件流程验证记录标注用途并从正式规则优化摘要排除，完整日志仍保留。测试需同时隔离 `DSH_WORKING_VERSION_ROOT` / `DSH_SESSION_ROOT` / `DSH_WORKSPACE_ROOT` / `DSH_AUDIT_ROOT` / `DSH_LEGACY_ROOT` / `DSH_INGESTION_ROOT` / `DSH_JOB_ROOT` 七个存储目录。上传记录校验所属存储上下文；整个项目按相同相对结构迁移仍可核对。已知旧服务记录可通过离线迁移工具导入，只读历史与当前稿分离；13条从核对原稿重新接入，不能推断已不可取的旧工作字节。稿件执行并发由 `DSH_REVIEW_WORKERS` 控制，账户API请求池与窗口补审继续按G5独立推进。

页面仅在成功确认服务能力后导入。健康检查失败或服务版本未知会明确阻止导入，恢复连接后重新确认；只有成功确认的旧服务才使用旧上传协议。恢复上传不会自动启动模型审阅，也不会用初次上传快照覆盖后续修改或人工记录。

零依赖：不需要 `npm install`，只用 Node 内置模块（`node:http`、`node:zlib`、`node:fs`）。要求 Node ≥ 18。

模型凭据仅从服务端环境变量 `ARK_API_KEY` 读取；可选 `ARK_BASE_URL`、`ARK_MODEL`。未配置凭据时仍可使用规则检查。页面关闭「模型深度审阅」后，会一并禁用模型复核与上下文调用，即使默认自证开关仍勾选也不会请求模型。直接 API 仍可显式设置 `useModel:false,useRecheck:true` 单独复核规则建议。用量统计包含深度审阅、自证及补问。

命令行批量审阅：

```powershell
node tools/cli-review.mjs "稿件.docx"                          # 规则 + 模型
node tools/cli-review.mjs "稿件.docx" --no-model               # 仅规则（秒级，不联网）
node tools/cli-review.mjs "稿件.docx" --model=deepseek-v4-pro-ga-260813 --json=out.json
node tools/acceptance.mjs "稿件.docx"                          # 含与历史批注的覆盖对照
node tools/selftest.mjs                                       # 自检（55 项）
node tools/api-e2e.mjs "稿件.docx"                             # 端到端 API 测试

# 批量验证（对全语料跑，见「批量验证」一节）
node tools/batch-verify.mjs                                   # 632 份解析+扫描（约 17—24 秒）
node tools/api-batch.mjs --count=632                          # 632 份 HTTP 全链路（约 22 秒）
node tools/stream-check.mjs                                   # SSE 流式接口：顺序、时序、与 /api/review 一致性
node tools/model-batch.mjs --count=3                          # 模型链路（分钟级）
```

> **中文路径提示**：PowerShell 在传递含中文的长路径给 `node` 时会破坏编码。
> 因此命令行工具支持用 `--pick=N`（按历史批注数排序后的第 N 份稿件）或 `--sha=<sha256>`
> 指定稿件，由程序从语料清单 `data/corpus/manifest.json` 解析真实路径
> （该清单由原项目批量工具生成，**本包未包含**，只带 3 篇样例；接续开发时直接传文件路径即可）：
>
> ```powershell
> node tools/cli-review.mjs --pick=8 --no-model
> node tools/acceptance.mjs --pick=8 --model=deepseek-v4-flash-ga-260731
> ```

## 它依据什么审稿

规则库不是凭空写的，来自两处真实来源：

**一、《东方学刊》体例规范**（`00-体例与规范` 文件夹）

| 规范文件 | 转化为 |
| --- | --- |
| 《东方学刊》发文形式规范（2023年版） | 论文七要素、标题编号顺序、专有名词外文备注、著作与篇名格式、段落格式、页下脚注体例、十类注释著录附例 |
| GB/T 15834-2011 标点符号用法 | 标点符号类规则 |
| GB/T 15835-2011 出版物上数字用法 | 数字与年代类规则 |
| CY/T 170-2019 学术出版规范 表格 | 表格类规则 |
| CY/T 171-2019 学术出版规范 插图 | 插图类规则 |
| CY/T 173-2019 关键词编写规则 | 关键词类规则 |

**二、历史一审稿件的真实批注**（`发给皓天的一审文件` 文件夹）

对 2024 年秋至 2026 年秋共 **598 份** Word 一审稿件做了结构化提取：

- **8687 条**责编批注（去重后 **2316 种**表述）
- **27190 处**段落级修订对照（修订前文本 → 修订后文本）
- 覆盖期号：05-2024年秋、06-2024年冬、07-2025年春、08-2025年夏、09-2025年秋、10-2025年冬、11-2026年春、12-2026年夏、13-2026年秋

提取出的批注按 15 个主题聚类（内容-政治把关 3770、格式-注释著录 1926、内容-事实核查 1756、内容-译名与专名 1406、语言-语病搭配 1082、语言-词汇用词 1000、语言-逻辑结构 914、格式-标题与编号 531、内容-学术规范 505、格式-图表 334、格式-标点符号 304、格式-数字用法 263、格式-摘要关键词作者 234、格式-网络来源 169 等），再由规则归纳产出可执行规则。

**当前规则总量：格式体例 82 条（FMT 42 条 + FMTB 40 条）+ 语言词汇 25 条 + 引文注释 31 条 = 138 条**。规则正文、规范依据和历史批注证据可在规则页查看。

原项目的完整资产账本（`data/optimization/task-ledger.json`、`derived-assets.json`）与旧 DOC/PDF 保真转换的推进计划**未随包提供**。当前界面仍只接收 DOCX；旧 DOC 需先另存为 DOCX，PDF/OCR 入口属于后续开发范围。

### 清洗与历史恢复

上传清洗失败明确返回 422，不回退原稿并报成功。清洗后重新解析实际保存字节，原稿批注数量与当前稿数量分开显示；没有可验证证明的历史稿须先点“验证清洗”。清洗变更形成可撤销保存版本，无变更只保存证明；失败或保存冲突不提交。

已知旧记录的迁移入口为 `tools/migrate-legacy-sessions.mjs`，要求已封存选择清单和新的证据输出路径；不会调用模型。`DSH_LEGACY_ROOT` 可隔离不可变历史存储。历史审阅只读，原始捕获、完成标记、原稿来源及实际可取工作文件独立保留。旧文件不可取时只从验证原稿重新接入，不把历史问题当本轮结果。

空命名工作台保持隔离；只有默认工作台兼容读取旧全局会话。单篇/批量失败均登记，刷新仍可见；服务登记失败则标为仅保存在本地。完整全量语义与全浏览器验收仍依长期路线推进。

### 规则的实际执行状态

138 条不等于 138 条都能自动跑。当前执行状态以 `/api/rules` 与规则页为准：

| 状态 | 条数 | 含义 |
| --- | --- | --- |
| **规则引擎** | 85 | 由确定性扫描器执行 |
| **未触发** | 3 | 判据有效，在现有语料中未触发；规则页说明原因 |
| **模型判断** | 19 | 三类规则库中的 `detect.type = "model"` 规则交给模型 |
| **人工复核** | 31 | 需结合上下文人工判断 |
| **合计** | **138** | |

之所以要标出「人工复核」，是因为格式体例规则里带 `detect.patterns` 的很多只是**描述用的例子**，
扫描器并没有读取它们（例如 FMT-040 古籍书名间隔号、FMTB-010 年代刊例写法、FMTB-012 作者简介格式，
在全语料 632 份稿件上从未命中）。把它们算作自动化能力属于虚高。

## 三层审阅架构

```
┌─────────────────────────────────────────────────────────┐
│ 1. 确定性规则引擎（秒级，不联网，零误报导向）              │
│    · 格式体例 80 条  → src/scanner-format.js             │
│    · 语言词汇 25 条  → src/scanner-language.js           │
│    · 引文注释 30 条  → src/scanner-citation.js           │
├─────────────────────────────────────────────────────────┤
│ 2. 大模型语义审阅（火山方舟 Responses API）               │
│    · 语病、逻辑论证、事实核查、引文核对、题文相符           │
│    · 长文按章节窗口切分，JSON Schema 约束输出              │
│    · 内容审核拦截时自动换模型 + 切窗兜底                   │
├─────────────────────────────────────────────────────────┤
│ 3. 人工复核                                              │
│    · 报告末尾给出人工复核提示                            │
│    · 被平台审核拦截的段落明确列出段落号                    │
└─────────────────────────────────────────────────────────┘
```

设计取向：**能用确定性规则判断的绝不用模型**（可复现、零成本、零幻觉）；模型只做规则做不到的语义判断。

## 网页界面

界面为**三栏布局**，两侧栏都可折叠（折叠后收成一条窄轨，轨上有「展开」按钮），窄屏（≤1024px）自动改为抽屉，顶栏按钮开关。

**左栏：审阅面板**
- 稿件卡片：标题、**栏目、作者**、字数、段落数、脚注/尾注数、已有批注数
- 审阅进度：逐阶段显示，带实时计时器（模型审阅耗时以分钟计，没有计时用户会以为卡死）；顶栏「中止」按钮可随时中断

**中栏：文档阅读器**
- **批阅视图**与 **Word 视图**共用同一套文档渲染器（`renderDocument()` + `docx-preview`），只是传入不同的渲染选项：批阅视图关页眉页脚，Word 视图完整渲染。不再维护两份渲染代码。
- **批阅视图**（默认）：渲染真实 Word 排版，命中问题的段落加底色与左侧色条（`.mk-hit`）；点击问题清单会滚动到对应位置并闪烁。
- **Word 视图**：完整还原 Word 排版，含页眉页脚、表格、脚注与尾注。
- **对比视图**：左「原稿（修订前）」右「建议稿（接受修订后）」，删除内容红色删除线、新增内容绿色下划线，段落按标题/正文/摘要/关键词分角色排版。无修订痕迹的稿件左右一致（这是正确结果，不是渲染失败）。
- **规则管理**：138 条规则，可按分组与**执行状态**（规则引擎 / 模型判断 / 人工复核）筛选、搜索、逐条展开查看依据与反例。

**右栏：问题清单 + 详情**
- 顶部统计条：总条数与按引擎分布、严重度分布
- 搜索框 + 折叠式「更多筛选」：分组（格式/语言/引文/模型）、严重度、只看可自动修复、只看已勾选、全选可修复
- 问题列表：按严重度排序，勾选框只对可自动修复项可用
- 点选问题 → 栏内展开详情（原文、问题、建议、改写、依据）+「追问模型」
- 底部「应用勾选的自动修复」；折叠后窄轨上显示问题数徽标

**勾选状态**：问题清单与批量修复**共享同一份 `state.accepted`**，筛选/重渲不会丢失勾选。

### 流式批注

审阅结果不是「等全部跑完再一次性刷出」，而是通过 SSE（`GET /api/review-stream`）逐条推送：

| 事件 | 内容 |
| --- | --- |
| `doc` | 整篇文档（段落/脚注/尾注），前端先渲染出批阅视图骨架 |
| `progress` | 阶段进度（规则扫描、模型逐窗） |
| `issue` | 一条问题（带 `seq`），前端收到即插入对应段落 |
| `done` | 去重后的**权威**问题清单，与 `POST /api/review` 完全一致 |

顺序严格按阅读顺序：**标题 → 正文段落 → 脚注 → 尾注 → 文档级判断**（缺内容提要、作者简介缺失等归到标题块下方）。已用脚本断言校验过 0 处逆序、脚注全部排在正文之后。

规则引擎本身是瞬时的（整篇约 45 ms），不加节奏的话前端会一次性刷出全部批注，看不出「逐条出现」。因此服务端按命中总数自适应插入 6—60 ms 的间隔，把规则阶段摊到约 2.5 秒；模型阶段则是**每完成一个窗口就把该窗口的批注推过来**，长稿不必等整篇跑完。

前端按 `issueKey` 即时去重，避免批注「先出现、完成时又消失」；`done` 到达后再用权威清单整体替换并全量重渲染，保证与服务端结果一致。

## 模型接入

使用火山方舟 Responses API。API Key 只在服务端从环境变量读取，不下发到浏览器，代码里**没有任何内置值**——默认不内置，需自行配置 `ARK_API_KEY` 才能启用模型审阅；不配置时规则审阅完全离线可用。

```powershell
$env:ARK_API_KEY="<你自己的火山方舟 API Key>"                  # 必填：不填则仅规则审阅
$env:ARK_MODEL="deepseek-v4-1-flash-260910"                   # 可选，默认同此
$env:PORT="3210"                                              # 可选
npm start
```

可选模型（页面右上角切换）：

| 模型 | 定位 |
| --- | --- |
| `deepseek-v4-pro-ga-260813` | 质量最高，推荐正式审稿 |
| `deepseek-v4-1-flash-260910` | 速度快，日常一审（默认） |
| `glm-5-3-flash-260828` | 长文经济，内容审核较宽松 |
| `deepseek-v4-flash-ga-260731` | 通用 |
| `doubao-seed-2-1-pro-260915` | 多模态，可读图 |

**关于内容审核**：火山方舟对涉政治表述的输入有内容审核，本刊作为政论性刊物，部分段落可能被拦截。智能体实现了三级兜底：换模型 → 把窗口切半递归重试 → 仍不通过则在报告中列出被拦截的段落号，明确标记「需人工审阅」，**不会静默漏审**。

### 调用这些模型时必须注意的三件事

这三点都是实测踩出来的，写在这里以免后续改动重新引入：

**一、不要传 `json_schema`（结构化输出）。**
这些是推理模型。一旦请求带上 `json_schema`，模型会把全部输出额度耗在思维链上——`reasoning_tokens` 恰好等于上限、`output_tokens` 也等于上限，而最终 `text` 是**空字符串**，且换任何模型都一样。实测同一个窗口：带 schema → 输出 16000 tokens、文本长度 0；不带 schema → 18 秒返回完整结果。
因此本项目改为**在提示词里明确要求 JSON 输出格式**，再用 `parseJsonLoose()` 容错解析（会依次尝试直接解析、剥离 Markdown 代码块、截取首尾花括号、逐个花括号配对扫描）。

**二、输出额度必须明显大于思维链所需。**
额度是「思维链 + 最终 JSON」共用的，窗口越大思维链越长。实测数据：

| `max_output_tokens` | 思维链 | JSON 输出 | 结果 |
| --- | --- | --- | --- |
| 8000 | 8000 | 0 | ✗ 返回空文本 |
| 12000 | 6605 | 7943 | ✓（10 段窗口） |
| 24000 | 8672 | 12107 | ✓（20 段窗口） |

因此额度统一设为 28000，同时把单个窗口限制在「10 个段落 / 1500 字」以内。窗口之间用 3 路受控并发（并发 4 会频繁触发 429），每个窗口 300 秒独立超时；返回内容解析失败时先用精简模式（最多 8 条、说明限 60 字）自动重试一次，仍失败才记入 `errors` 并在界面上提示——**绝不静默产出 0 条**。

**三、中止必须立即生效，不能进退避等待。**
`abort(reason)` 会让 `fetch` 以那个 reason 拒绝，此时 `err.name` 是 `'Error'` 而不是 `'AbortError'`。
若重试循环只靠错误名判断中止，就会把「已中止」当成可重试错误，睡满 7 次指数退避（≈132 秒）才抛出——
实测用户点「中止」后服务端要 **140 秒**才真正停下。
因此 `arkRequestWithRetry` 在**每次循环开头**先检查 `signal?.aborted` 并立刻抛出；
`modelReview` 用 `AbortSignal.any([整次审阅的中止信号, AbortSignal.timeout(窗口超时)])`
把两个信号合成一个传给每个窗口。修复后中止 **1.0 秒**生效，且可立即重跑。

## API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/health` | 服务状态、可用模型、规则条数 |
| GET | `/api/rules` | 全部规则库（含执行状态）、审稿提示词、状态汇总 |
| POST | `/api/upload?name=x.docx` | 上传并解析稿件，返回 sessionId 与结构化文档 |
| POST | `/api/review` | `{id, useModel, model, focus}` 执行审阅；加 `async: true` 则返回 202 受理回执，由前端轮询取结果 |
| **GET** | **`/api/review-stream?id=&useModel=&model=`** | **SSE 流式审阅**，事件序列 `doc → progress → issue* → done`（网页端默认走这条） |
| GET | `/api/review-status?id=` | 异步审阅的进度与结果（`{running, progress, error, result}`） |
| POST | `/api/cancel-review` | `{id}` 用 AbortController 真正中止在途的模型请求 |
| GET | `/api/review-requests` | 请求池核对视图：逐笔列出「发送结果未确认」的请求（含所属审阅是否已被中止）及当前并发占用 |
| POST | `/api/review-requests/abandon` | `{attemptIds, acknowledge}` 经真人逐字确认后释放未知占位：只标记「结果与费用按未知处理」，不确认响应、不自动重发，原始回执保持不变 |
| POST | `/api/report` | 生成 Markdown 审校报告（同时落盘到 `reports/`） |
| POST | `/api/ask` | `{id, question, context, useModel}` 追问；`useModel: false` 时走规则库直答（毫秒级，不调模型） |
| POST | `/api/apply-fixes` | `{id, accepted}` 应用勾选的自动修复 |
| POST | `/api/export-docx` | 在当前工作版本导出问题批注；可传 `accepted`、`baseVersionId`、`baseReviewRunId`。返回产物散列和导出身份，来源范围、实际放置及未导出原因持久记入审计。 |
| GET | `/api/export-placement?id=&exportId=` | 回读该会话的服务器导出凭证；区分问题条数、实际批注处数、原始字符范围及替代位置。 |
| GET | `/api/export-working-docx?id=` | 下载当前工作版本的真实字节，包含已经保存的修改。 |

> **为什么 `/api/review` 需要异步模式**：模型审阅一份 623 段的稿件约需 460 秒，
> 而 Node `fetch` 的 `headersTimeout` 默认 300 秒，同步模式必然超时崩溃
> （实测 `UND_ERR_HEADERS_TIMEOUT`）。`/api/review-stream` 天然规避了这个问题
> （首字节立即返回，之后持续推送），网页端默认走流式接口。
>
> **持久任务与取消**：三种审阅入口共用持久任务。SSE 连接用于观察进度；页面断线或关闭后，服务器继续执行。点击取消会写入当前任务的取消意图，由执行者中止在途请求。发布提交后的取消会明确返回未接受，保存的结果与运行记录仍可回读。
>
> **中止为何可能挡住后续审阅**：中止会让「已物理发出、但没取回响应」的在途请求落为 `unknown_sent`。设计上它们既不能当作未发送（可能已被计费），也绝不自动重发，因此各占 1 个并发名额；占满并发上限后，新的模型审阅会被 409 `ARK_EXECUTION_BLOCKED` 拒绝，且刷新重试无效。处置只能由人完成：`GET /api/review-requests` 核对每一笔的来源，`POST /api/review-requests/abandon` 逐字确认后释放名额（网页端在左侧队列里有同样的入口，并会写下一份可校验的人工授权证据）。释放只声明「结果与费用按未知处理」，原始回执与发送字节保持原样可追溯。若只想先跑规则检查，可在取消勾选「模型深度审阅」后审阅——纯规则审阅不占用请求池。
>
> **并发上限本身也是安全阀**：上限过高会浪费账户并发，过低则「一次中止留下的两笔未知」就能堵死整个池（2026-10-13 反复发生）。变更上限只允许走留痕通道：
>
> ```bash
> node tools/set-ark-pool-policy.mjs --concurrency=6 \
>   --reason="上限 2 时一次中止即可堵死全部名额" \
>   --authorization-quote="<操作者授权原话>"
> ```
>
> 该工具先写一份不可变授权证据（`reports/ark-pool-policy-change-*.json`）与一份不可变变更事件（`pools/<poolId>/policies/<operationId>.json`），再在同一次加锁提交里更新账本；要求池内没有在途或排队请求，并用「当前字节 + 当前版本」做 CAS。**不要**手改 `state.json` 里的 `policy`，也不要用 `DSH_ARK_POOL_CONCURRENCY` 覆盖已登记的值——后者会被 `ARK_POLICY_CONFLICT` 拒绝；前者会在读取时被 `ARK_POLICY_CORRUPT` 抓出来（账本上限必须等于最后一次留痕变更的目标值）。回归测试见 `tools/test-ark-pool-policy.mjs`。

Word 不显示脚注或尾注内的范围批注。本系统把注释问题的 Word 批注放到正文中经过核验的实际注号引用，同时在批注及导出凭证中保留原注身份和原文范围；网页中的字符标注与 Word 的替代位置分别说明。缺少可靠引用、来源变化或位置歧义会保留未导出原因。[Word 对注内批注的限制](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/84a35ef3-9c12-4b59-ab4c-4a88f520d06c)。

## 隐私与安全

- **原始稿件永不被改写**：原目录只读，自动修改写入独立且可追溯的工作版本。
- **API Key 不下发浏览器**：所有模型调用经服务端代理。
- **零第三方依赖**：无供应链风险；ZIP 读取有解压体积上限（300MB），防止 zip 炸弹。
- **派生记录在本机保存**：开启模型审阅时，所需稿件上下文经服务端发送到已配置的方舟服务；关闭模型时运行本地规则检查。
- **会话内存受控**：40 个为内存缓存上限，持久会话不会随缓存淘汰而删除；打开稿件时按保存身份与哈希恢复。

## 已知边界

1. 需回原始文献核对的问题（引文页码、数据来源、经典著作版本、译名对错），规则引擎与模型都只能提示「须核对」，不能替代查证。
2. 图内文字无法用规则引擎检查，需多模态模型。
3. 自动修复只覆盖确定性规则（标点、年代写法、约数写法等）；语义类问题只给建议。
4. 旧版 `.doc` 文件需先另存为 `.docx`。
5. 规则引擎的召回率是「下限」：它只报确定命中的模式。历史一审批注中大量是「数据似有出入，请郭老师把关」这类**向作者提问的语义判断**，规则无法覆盖，这部分由大模型承担——因此模型审阅不是可选项，建议正式审稿时保持开启。
6. 带修订痕迹的稿件按「接受修订后」的文本审阅（`text`），`before` 保留原始文本用于左右对照。
