# 《东方学刊》审稿智能体 · 验收目标

本文件是本项目的验收标准。每条都有可复现的验证方法。

> **交接包说明**：本文件由原项目同名文档整理而来，仅做两处处理：① 未纳入任何服务器部署与账号凭据内容（原文本身亦无此类内容）；② 把指向原项目内部数据目录/历史验证产物的路径改为文字说明。文中出现的 `data/verify/`、`data/optimization/` 等只表示脚本的**落盘输出位置**（运行时自动生成），本交接包未预置这些历史产物；`00-体例与规范/`、`发给皓天的一审文件/样例/` 在包根目录下与本文件同级。

## 一、验收总目标

做一个能在网页中驱动运转的《东方学刊》审稿智能体，具备四项能力：

1. **导入文档** —— 拖拽或选择 `.docx`，自动解析并保留原稿结构。
2. **左右预览修改前后** —— 左栏原稿、右栏建议稿，逐字显示修订痕迹与删除/新增标记。
3. **格式体例审阅** —— 依据 `00-体例与规范` 文件夹的六份规范，逐条检查格式问题。
4. **内容基本错误审阅** —— 依据 2024 年秋以来历史一审稿件的批注，检查语法、语病、词汇、逻辑、引文、事实问题。

**最终验收判据**：找一篇文章，能够**完整识别全部格式问题**，并且**基本识别出内容上的问题**。

## 二、规则库验收

| 项 | 要求 | 当前 | 验证方法 |
| --- | --- | --- | --- |
| 格式体例规则 | ≥ 30 条，可自动执行 | **80 条**（FMT 40 条确定性规则 + FMTB 40 条历史批注归纳的编辑惯例） | `GET /api/rules` 或页面「规则库」标签 |
| 语言词汇规则 | ≥ 25 条，含正则与词表 | 25 条 + 100+ 词条 | 同上 |
| 引文注释规则 | ≥ 20 条 | 30 条（其中 19 条为精确违规判定） | 同上 |
| 历史批注归纳 | 覆盖全部 8687 条批注 | 598 份稿件 / 8687 条批注 / 2316 种表述 | `data/comments/occurrence-stats.json`（原项目历史产物，未随包提供） |
| 规则可溯源 | 每条规则标明规范条款或批注出处 | 是 | 页面规则库每行显示「依据」 |
| **规则总量** | — | **135 条** | 页面「规则库」视图，可全文搜索 |
| **执行状态如实标注** | 不得把未实现的规则算作自动化能力 | **83 自动检测 / 9 模型判断 / 43 人工复核** | 页面「规则库」页状态标签与筛选 |

> **关于「135 条」的口径**：135 是规则库的登记总量，不等于 135 条都能自动执行。
> 页面按执行状态如实区分——**83 条由规则引擎自动检测，9 条交模型做语义判断，43 条需人工复核**。
> 之所以要单独标出「人工复核」，是因为格式体例规则里带 `detect.patterns` 的很多只是**描述用的例子**，
> 扫描器并未读取（例如 FMT-040 古籍书名间隔号、FMTB-010 年代刊例写法、FMTB-012 作者简介格式，
> 在全语料 632 份稿件上从未命中）。把它们算作自动化能力属于虚高。

**格式规则必须完整覆盖** `00-体例与规范` 六份规范的以下方面：
论文构成要素与次序、各级标题编号顺序、专有名词与外文备注、标点符号用法（GB/T 15834-2011）、
数字用法（GB/T 15835-2011，含「年代统一写 1990 年代」「约数用中文数字」）、
表格规范（CY/T 170-2019）、插图规范（CY/T 171-2019）、关键词编写规则（CY/T 173-2019）、
段落格式、著作与篇名格式、页下脚注体例、十类注释著录附例。

## 五、端到端验收方法

```powershell
cd dsh
npm start
# 浏览器打开 http://127.0.0.1:3210
# 1. 导入稿件  2. 开始审阅  3. 查看左右对照与问题清单  4. 导出报告
```

命令行验收（可批量跑）：

```powershell
node tools/cli-review.mjs "稿件.docx" --model=deepseek-v4-pro-ga-260813
node tools/acceptance.mjs "稿件.docx" --model=deepseek-v4-pro-ga-260813
```

`tools/acceptance.mjs` 会输出：
- 规则引擎与模型各自命中的问题数
- 与历史批注的**方面覆盖率**（17 个方面，逐项对照批注是否提及、智能体是否发现）
- 与真实修订痕迹的**位置重合率**

**与真实修订位置的重合率 52%** 意味着：责编实际动过修订的 98 个段落中，有 51 个也被智能体报出了问题。该指标只统计「段落级重合」，而历史修订中包含大量纯润色（改标点、调语序、删冗余字）与排版动作，本身不是「错误」；因此 52% 是一个偏保守的下限，不等于遗漏率。

**模型发现的真实问题样例**（均已核对原文属实）

| 类别 | 原文 | 问题 |
| --- | --- | --- |
| 成分赘余 | 今年恰逢中国研究院成立10周年之际 | 「恰逢」已含「正赶上」之意，后接「之际」语义重复 |
| 事实核查 | 距离「午夜」还有17.5分钟 | 前文写「17分钟」，此处「17.5分钟」，前后矛盾；据《原子科学家公报》1991 年实为 17 分钟 |

| 并列不当 | 非洲、印度、南亚、中亚或拉丁美洲这些地区 | 「印度」是国家且属于「南亚」，与地区概念并列造成包含关系 |
| 搭配不当 | 冷战结束反而恶化了这种意识形态 | 「恶化」为不及物动词，不能带宾语 |
| 搭配不当 | 美国还坐拥太平洋和大西洋两大洋的保护 | 「坐拥」与「保护」搭配不当 |
| 关联词 | 因为美国代表正义力量，因此，应该由美国制定规则 | 「因为」与「因此」连用造成逻辑冗余 |
| 成分残缺 | 由于科技、教育、基础设施的进步，能够取得巨大的发展成就 | 冒号后「能够取得」缺主语 |
| 结构杂糅 | 当前的地缘政治，尤其是……之间的关系正处于……时期 | 「当前的地缘政治」后无谓语，与「尤其是」引出的成分杂糅 |

### 6.6 验收过程中发现并修复的功能缺陷

以下缺陷都是靠端到端实测才暴露的，规则自检与单元自检都不会发现：

| 缺陷 | 表现 | 根因 | 修复 |
| --- | --- | --- | --- |
| **结构化输出导致模型返回空文本（最关键）** | 模型审阅在全部窗口上返回 0 条问题，且**换任何模型都一样**；但同一段文本改用普通文本调用却能 18 秒正常返回 | 调用方传了 `json_schema`（结构化输出）。这些是推理模型，一旦带上 schema，就会把全部输出额度耗在思维链上，`reasoning_tokens` 恰好等于上限、`output_tokens` 也等于上限，而最终 `text` 为空字符串。实测：budget=8000 → 思维链 8000、文本 0；去掉 schema 后同一请求 18 秒返回完整结果 | 去掉 `schema` 参数，改为在提示词中明确要求 JSON 输出格式，再用 `parseJsonLoose` 容错解析（已加强为「逐个花括号配对」扫描） |
| **输出额度与思维链争抢** | 即使去掉 schema，窗口稍大仍会返回空文本 | 额度是「思维链 + 最终 JSON」共用的。实测 budget=8000 时思维链吃满 8000、JSON 为 0；budget=12000 时思维链 6605、JSON 7943（成功）；budget=24000 时思维链 8672、JSON 12107（成功）。额度必须明显大于思维链所需 | 额度定为 28000，同时把窗口限制到「10 个段落 / 1500 字」以内，避免思维链膨胀 |
| **窗口切分失控** | 短段落挤进同一窗口，实测出现 231 个段落的窗口；请求过大导致返回被截断 | `buildWindows` 只按字数切分，且超出上限后会把窗口重新等分合并，进一步放大单窗规模 | 窗口同时受「字数」与「段落数」两个上限约束；超长段落单独成窗；取消等分合并逻辑 |
| **解析失败静默吞掉** | 模型审阅显示「命中 0 条」，看不出任何异常 | 解析失败后直接 `continue`，既不记错误也不提示 | 解析失败先记入 `errors` 并在进度中提示，再用精简模式（限 8 条、说明限 60 字）自动重试一次 |
| **串行调用过慢** | 24 个窗口串行审阅耗时超过 40 分钟且频繁超时 | 窗口之间本无依赖，却按顺序逐个调用 | 改为 4 路受控并发，并为每个窗口设 300 秒独立超时；总耗时降到 462 秒 |
| **自动修复静默失效** | 网页勾选问题后点「应用自动修复」，提示应用 0 项 | 前端 `issueKey` 用 `quote.slice(0,40)` 构造键，服务端用完整 `quote` 匹配，两边不一致 | 统一为 `${ruleId}\|${location}\|${quote}` 不截断 |
| **批注无法定位** | 验收统计显示批注位置覆盖率为 0% | `parseComments` 只读了批注文本，没有把批注挂到它锚定的段落上 | 建立「批注 id → 锚定段落」映射，为每条批注补上 `paragraphIndex`、`anchorText` |

修复后：`tools/selftest.mjs` 55 项全部通过；`tools/api-e2e.mjs` 端到端 29 项全部通过；模型审阅 24 个窗口全部正常返回；历史批注方面覆盖率从 63% 提升到 88%；自动修复可实际改写右栏文本。

### 6.8 批量验证中发现并修复的缺陷

| 缺陷 | 表现 | 根因 | 修复 |
| --- | --- | --- | --- |
| **`/api/ask` 忽略 `useModel:false`，每次追问都调模型** | 20 份稿件实测该接口中位耗时 **11 112 ms**、最大 20 858 ms，是全链路唯一瓶颈；632 份全链路验证要 251 秒（仅 20 份时） | `server.mjs` 的 `/api/ask` 分支无条件调用 `arkChat()`，请求体里的 `useModel:false` 被完全忽略 | 新增 `ruleBasedAnswer()`：`useModel === false` 时直接从本次审阅结果归纳答案（按规则归并 Top 类、给出依据与改写示例）。耗时降到 **0—3 ms**，632 份全链路总耗时降到 **22.4 秒** |
| **同一段落多处修复互相失效，2 条修复被静默丢弃** | 吴畅畅《政治化的主体及其狂热》一份稿件就有 1 条判为「未产生变化」而丢弃；全语料 1395 条可修复项里有 2 条丢失 | `/api/apply-fixes` 按结果数组原顺序逐条改写。同段落有多处待改时（如一段里 3 处 `...` 都要改成 `……`），前面的替换让后面记录的 `offset` 全部偏移，精确匹配失败后退回 `indexOf`，改到第一个出现位置或判为无变化 | 两处：`applyFixToText` 在精确偏移失效时改为选择**离记录偏移最近**的那一处；`/api/apply-fixes` 先按目标段落分组、组内**按偏移从后往前**应用。修复后 1395 条 **100% 应用** |
| **模型审阅超过 HTTP 客户端超时（长稿必失败）** | `node tools/api-e2e.mjs --pick=8` 直接以 `UND_ERR_HEADERS_TIMEOUT` 崩溃 | 模型审阅 623 段稿件约需 460 秒，而 Node `fetch` 的 `headersTimeout` 默认 300 秒 | `POST /api/review` 支持 `async: true`（立刻返回 202 受理回执），前端轮询新增的 `GET /api/review-status`；新增 `POST /api/cancel-review` 用 `AbortController` 真正中止在途请求。同步模式保留供脚本使用 |
| **429 限流导致部分窗口审阅失败** | 并发 4 个窗口时实测 11 个窗口里 2 个返回 `429 ModelAccountRateLimitExceeded`，日志记为「审阅失败（已记录）」，这些段落的内容没有被模型看到 | 并发偏高、退避不足 | `arkRequestWithRetry` 重试 5 → 7 次、退避封顶 30 秒、优先采用服务端 `Retry-After`；`modelReview` 并发 4 → 3。**修复后实测 429 失败 0 次，模型命中数从 98—125 条回升到 171—332 条** |
| **「中止」点了没用，服务端 140 秒后才停下（最难查）** | 点中止后前端退出了等待，但服务端仍在把所有窗口跑完；`/api/review-status` 16 秒后仍返回 `running: true`，且期间无法重新发起审阅（「该稿件正在审阅中」） | 两层原因叠加：① `modelReview` 的 `handleWindow` 为每个窗口各建一个 `AbortController`，**外层中止信号从未传进来**；② `abort(reason)` 会让 `fetch` 以那个 reason 拒绝，此时 `err.name` 是 `'Error'` 而非 `'AbortError'`，而 `arkRequestWithRetry` 只靠错误名判断中止，于是把「已中止」当成可重试错误，睡满 7 次指数退避（≈132 秒）才抛出 | 三处：`arkRequestWithRetry` 每次循环开头先查 `signal?.aborted`（已中止立刻抛出不退避），catch 里也先查中止状态，新增 `abortReason()` 取可读原因；`handleWindow` 改用 `AbortSignal.any([外层信号, AbortSignal.timeout(窗口超时)])`；`reviewWindow` 入口先检查中止状态且中止不再记成「窗口审阅失败」。**实测中止从 140 秒降到 1.0 秒生效，且可立即重跑** |
| **会话只增不减，内存持续增长** | 批量验证跑完 632 份稿件后 `/api/health` 显示 `sessions: 609`；每个会话同时持有文档对象与**原始文件 Buffer**（长稿数 MB），全部留在内存里 | `server.mjs` 的 `sessions` Map 没有任何淘汰逻辑 | 新增 `MAX_SESSIONS = 40` 与 `evictSessions()`，按「最近使用时间」淘汰（**正在审阅的不淘汰**）；新增 `touchSession()` 在 6 个接口统一刷新使用时间。实测连续上传 60 份后会话数稳定在 40 |
| **脚注类问题定位全错：编号错位 + 反查取到另一条脚注（最隐蔽）** | 报告同一行写着「位置：footnote:0（第 1 条脚注）」自相矛盾；网页端点击脚注类问题高亮的**不是**那条脚注 | DOCX 的 `footnotes.xml` 含 `separator`/`continuationSeparator` 条目，引文扫描器又过滤掉空脚注，于是同一条脚注有**三个互不相等的编号**（真实数组下标／过滤后数组下标／读者序号），代码在三者间反复混用：① 扫描器写出的 `footnoteIndex` 是过滤后下标，前端 `doc.footnotes[idx]` 反查**取到另一条脚注**；② `location` 用 0 基而下标、报告按 `+1` 换算，16 条全部错位；③ `findParagraph()` 命中脚注时故意返回 -1 并丢掉匹配结果，脚注类模型问题全标成 `document`；④ 模型提示词用 `[脚注0]` 编号，与正文脚注序号错位 | 五处：`scanner-citation.js` 新增 `origOf` + `fnLoc()`，统一产出真实 `footnoteIndex`／`footnoteNumber`／`location: footnote:N`（7 处构造全改）；`ark.js` 新增 `findLocation()` + `buildModelIssue()` 做三级定位，提示词改 `[脚注1]` 起；`review.js` 只输出 `location` 不再二次换算；`server.mjs` 的 `serializeDoc()` **补下发 `isNoteSeparator`**（此前根本没传给浏览器）；`app.js` 按真实注释计数并给分隔符加 `fn-sep` 灰显。**实测：16/16 反查原文全部对上，网页序号 1—18 连续，带标记序号与规则标签完全一致** |

### 6.14 未触发规则逐条定性 + 状态口径源码化（本轮）

`tools/classify-never-fired.mjs` 对 54 条从未触发的规则逐条定性，判定顺序是

| 类别 | 条数 | 含义 |
| --- | --- | --- |
| **A 未实现** | **38** | 规则库声明了，扫描器里没有对应检查代码 |
| **B 判据失效** | **0** | 有实现但构造样本也报不出 —— **本轮已清零** |
| **C 合法未触发** | **3** | 判据有效，只是真实语料没有这种情形 |
| **D 模型规则** | **9** | 设计上交给大模型 |
| **E 人工规则** | **5** | 声明即人工复核 |

C 类三条都验证过「构造样本能报出」：FMTB-018（图表说明用颜色区分）、

CIT-017（中文著作名未用书名号）。

**二、`detect.check` 只是设计意图，不是实现**

38 条 A 类规则的 `detect.check` 字段写着 `headingUniformity`、`paragraphIndent`、
`westernItalic` 这类函数名，看起来像已实现。实测：**15 个 check 名称里 14 个在源码中查无此物**
（唯一出现的 `funding` 还只是角色分类器，不是规则检查）。这些字段是设计时的意图记录，
不能当作「已实现」的证据。

**三、规则状态改为源码驱动，消除口径漂移**

`server.mjs` 原先用三份**手写**的 `IMPLEMENTED` 集合标注状态，漂移过三次：

| 漂移 | 现象 |
| --- | --- |
| `withStatus()` 的 `type === 'list'` 回退分支漏了 `group === 'language'` 前提 | 任何 `type=list` 的规则都被算成「自动检测」，含从未实现的 FMTB-032 |
| FMTB-018 有实现，却被排除在清单外 | 状态在 auto/manual 之间反复出错 |
| LANG-001 / LANG-006 明明在跑，却漏登记 | 自动检测数偏少 |

现在改为 `src/implemented-rules.js` **运行时扫描 scanner-\*.js 源码**推导，认两种实现方式：

1. **显式实现**：`R('FMT-010')`、`rules.get('LANG-017')`、`id: 'CIT-001'`、
   `push('CIT-020', …)`、`ruleId === 'LANG-016'`、`['LANG-008', '口语化词']`
2. **通用循环**：`scanner-language.js` 第 122—141 行会把**每一条** `type='list'` 规则的
   `detect.patterns` 跑一遍，所以「语言规则 + type=list + patterns 非空」也算实现

> 反向陷阱：LANG-008/009/013 也是 `type=list`，但 `patterns` 非空、确实在跑
> （语料命中 357 / 306 / 10 次）；真正被关掉的是另一套 `lexiconMap` 词表。
> 只看 `type` 不看 `patterns`，正是当初 FMTB-032 被错标的根因。

| I1 | 语料上触发过的规则必须被判为「会执行」 | ✓ |
| I2 | 判为「会执行」的规则不得与定性结果冲突 | ✓ |

### 6.18 规则管理双模式：提示词式规则真的交给模型（本轮）

**一、规则库天然分两类**

| 模式 | `detect.type` | 谁来判断 | 条数 |
| --- | --- | --- | ---: |
| **格式式** | `regex` / `list` / `structure` | 扫描器直接跑正则或清单 | 126 |
| **提示词式** | `model` | 大模型读规则原文、逐条语义匹配 | **9** |

9 条提示词式规则（LANG-002/004/005/011/014/019/022/023/024）每条只有一句 `detect.method` 判断要点。

**二、查出的真问题：提示词式规则从来没进过提示词**

1. `deterministicReview` 把 `modelRules` 放进返回值，**只给了前端**；`modelReview` 的提示词里没有规则清单 —— 模型是在「凭常识审稿」而非「按本刊规则逐条匹配」。
2. `buildModelIssue` 写的是 `ruleId: \`ARK-${it.category}\`` —— **凭分类名现造的合成号**。规则库里不存在 `ARK-xxx`，所以模型问题永远挂不到任何规则上，规则管理页里那 9 条 model 规则**永远显示 0 命中**。

**三、改法**

- 新增 `promptStyleRules()`：取 `detect.type === 'model'` 的规则，返回 `{id,title,method,severity}` 稳定清单。
- `modelReview` 注入规则段（调用方传入优先，否则自取），并回调进度 `注入提示词式规则 N 条（LANG-002、…）`。
- 提示词要求「优先归入上述规则号，不属于任何一条时 ruleId 留空」。
- `buildModelIssue` 校验 `ruleId` 形如 `/^[A-Z]+B?-\d{3}$/`，是则采用并置 `ruleMatched: true`。

**四、实测证据（真实调用方舟）**

| 「××刊**发排版**」 | 89 | 编辑部**已过审**、送排版 |
| 「××刊**责编版**」 | 469 | 仍在责编环节 |
| 「一审文件，发排版」 | 64 | 早期命名的同层 |
| 「毛条样，编务版」 | 10 | 已接受修订的无痕版 |

**坑一：拿批注数量当质量标签。** 实测排版版 0.05 条/千字、责编版 0.86 条/千字（Welch t = **−18.6**），有批注比例 4% vs 80%。但发排版版是**修订已接受、批注已清理**的版本，批注本来就被删了 —— 它反映「文件处于哪个工作流阶段」，不是「稿子好不好」。**历史批注只能用来理解编辑关注点，不能当质量度量。**

**二、两层差异：显著，但不足以做二元分类**

| 指标 | 排版（89） | 责编（469） | Welch t |
| --- | ---: | ---: | ---: |
| 总问题数/篇 | **17.9** | **21.7** | **−2.55（显著）** |
| 高严重度/篇 | 6.9 | 8.0 | −1.40（**不显著**） |

总问题数差异显著（低 17.5%），但 sd 都在 13 左右、重叠很大。**故做分级判定，不做二元分类器。**

**三、坑二：阈值比中位数还高**

第一版用已过审层 P75（53.6）当「合格」上限 → 全量 **89.2% 判不合格**。该阈值比全语料中位数（45.6）还高，等于要求「比一半稿件都干净才算合格」。改为**锚在已过审层中位数（35）**。

**四、坑三（最重要）：一票否决把 82% 的已过审稿毙了**

原先 `FMT-001`（构成要素缺失）设为一票否决。实测 **已过审 89 篇里有 73 篇（82%）也触发 FMT-001**。原因：该规则把「题目/作者/内容提要/关键词/简短引言/正文/作者简介」**七要素打包成一条**，缺任一即报；而提要、作者简介在原始投稿里常常没有（靠编辑部补），不是「稿件不合格」。

**结论：判定不看有没有触发某条规则，只看加权分**，`BLOCKING_RULES` 置空。

**五、判定分布与历史对照**

| 档位 | 全量 | 已过审层（89） | 在审层（543） |
| --- | ---: | ---: | ---: |
| 合格 | 219（34.7%） | 46（51.7%） | 173（31.9%） |
| 基本合格 | 155（24.5%） | 21（23.6%） | 134（24.7%） |
| 需修改 | 152（24.1%） | 14（15.7%） | 138（25.4%） |
| 不合格 | 106（16.8%） | **8（9.0%）** | **98（18.0%）** |

- 已过审层「合格+基本合格」**75.3%** vs 在审层 **56.5%**，差 **+18.7 个百分点**（方向正确）
- 判「合格」召回率 **67.6%**
- **已过审层被判「不合格」仅 9.0%**，是在审层（18.0%）的一半 —— 关键指标：判不合格时误伤已过审稿件的概率低
- 精确率 21.0% 是**下界**：「在审层」≠「不合格」，那 543 篇只是还没走到排版环节

**六、落地**

- `src/verdict.js`：`scoreIssues()` / `judge()` / `calibrate()` / `isTypesetPath()`
- `tools/verdict-report.mjs`：标定 + 全量判定 + 历史对照 → `data/verify/verdict-report.json`、`稿件合格性判定报告.md`

**七、修掉的三个缺陷**

1. `url.pathname` 不做百分号解码 → 项目路径含中文（「学术」）时变 `%E5%AD%A6%E6%9C%AF` 导致 ENOENT，改用 `fileURLToPath`

### 6.24 模型复核：每条修改都让模型再判一次（本轮）

**一、做法**：对每条「建议修改」再问一次模型 —— 问题是否真实存在、改法是否成立、有无更好改法。三档输出 `agree`/`disagree`/`unsure`。

| 决定 | 理由 |
| --- | --- |
| **批量复核**（每批 8 条） | 一条一请求要 20—40 次调用，且每次重发规则原文 |
| **只复核有具体改法的条目** | 文档级判断没有可核对的改写文本 |
| **要 JSON 但不传 `json_schema`** | 传了会让推理模型把预算全烧在推理链上，`text` 变空 |
| **复核失败不拖垮报告** | 记 `errors` 并继续，报告如实写「N 条未复核」 |

**二、踩到的坑：返回的 JSON 被从头截断**

第一轮 41 条全部返回「模型未返回该条结论」。抓原始输出：

```
usage: {output_tokens: 1236, output_tokens_details: {reasoning_tokens: 1060}}
text:  "results\":[{\"i\":0,\"verdict\":\"agree\",...     ← 开头的 `{"` 被吃掉
```

1. **推理链吃掉 86% 输出预算**（1060/1236），正文只剩 176 token。
2. `parseJsonLoose()` 的「逐个配对花括号」兜底会把数组里**第一个元素**当结果返回 —— 看着「解析成功」，实际丢了其余全部条目。

改法：新增 `salvageTruncatedHead()` 识别 `^"?<键>":` 形态并补回 `{"`（**只处理这一种可判定形态**，不做泛化猜测）；批次 12→8，预算 12000→20000，提示词要求「不长篇推理、reason ≤30 字」。

**修复后 41 条里 40 条拿到真实结论**，6 批共用 50 秒。

**三、复核直接抓出系统性误报**（模型的不同意理由高度集中）

| 规则 | 模型理由 | 查证 |
| --- | --- | --- |
| `FMTB-031` | 「已明示分母为美国人口」 | **真缺陷** |
| `LANG-010` | 「150 字阈值非刊例规范」「引文不宜擅拆」 | **真缺陷** |
| `FMT-024` | 「『20世纪80年代』符合国标」 | 规则成立，**严重度定错** |
| `FMTB-010` | 「『1965年以后』是时点，改年代会篡改原意」 | **真缺陷** |
| `FMT-006/007` | 「实为 4 个关键词，在 3—8 个范围内」 | **真缺陷** |
| `FMT-020` | 「原文为页码区间非年代区间」 | **真缺陷** |

| 阶段 | 同意 | 不同意 | 拿不准 | 合计 | 不同意率 |
| --- | ---: | ---: | ---: | ---: | ---: |

### 6.28 模型并发逐条匹配（目标点 12 后半）（本轮）

`ruleMode: 'per-rule'` —— 每个「窗口 × 规则」一个独立请求，提示词只讲一条规则，各自输出 JSON 再合并。UI 顶栏 `#ruleMode` 下拉（默认「整段通读」）；`POST /api/review` 与 SSE `?ruleMode=per-rule` 都支持。

**实测结论：`per-rule` 不是升级，默认必须是 `all`。**

同一份 12 段内容各跑一次：

| 模式 | 耗时 | 发现问题 | 挂到提示词式规则 | output_tokens |
| --- | ---: | ---: | ---: | ---: |
| `all` | 64.1 s | **4 条** | 3 条 | 22 052 |
| `per-rule` | 87.8 s | **2 条** | 2 条 | 33 880 |

per-rule 在 **1.54 倍输出 token、1.37 倍耗时**下**少发现一半**问题。

**成本量测**：并发 3 → 76.9 s（单任务 4.3 s）；并发 6 → 96.7 s（**反而更慢**，瓶颈是限流等待而非并发度）。长稿外推 40 窗口 × 9 规则 = 360 任务 ≈ 8.6 分钟，故设硬上限 `perRuleMaxTasks = 120`，超限按窗口优先截断**并在 `errors` 显式记录「仅执行前 N 个，其余未覆盖」**。

**顺手修掉的漏项**：per-rule 路径第一版没累加 token，整个路径 `usage` 恒为 `{input_tokens:0, output_tokens:0}`。

### 6.33 审阅流程做实：进度条 + 断线重连（目标点 5）（本轮）

**一、进度条**

模型阶段有确定的窗口总数 → **真实百分比**：`模型审阅 1/2 窗口（50%） · 约剩 1 分 24 秒`；规则扫描/准备阶段没有「窗口」概念 → **不确定进度**循环动画，而不是假百分比。

标签分三段判。第一版只按 `phase === 'model'` 判断，结果后端已在逐窗跑模型、前端还一直显示「模型准备」——实测 50 秒后进度条仍停在准备阶段，用户会以为卡住：

| 条件 | 标签 |
| --- | --- |
| model 开头 且 已完成 0 窗口 | 模型准备 |
| model 开头 且 已完成 >0 窗口 | 模型审阅（真实百分比 + 剩余时间） |
| recheck 开头 | 模型复核 |
| 其余 | 规则扫描 |

**二、断线重连 —— 修掉「一次 F5 作废十分钟」**

服务端原先 `req.on('close')` **一律 abort**。用户刷新页面、标签页被系统回收、笔记本休眠，一篇跑了 10 分钟的模型审阅就白跑（实测一篇 560—890 秒）。

新增 `detach=1`（前端默认开启）：断开只停止推送，**模型请求继续跑**，结果落到 `s.result`。真正的中止仍走 `/api/cancel-review` 显式 abort。

**三、刷新后恢复现场**（三步缺一不可）

| 需要什么 | 接口 | 不做会怎样 |
| --- | --- | --- |
| 会话还在不在、跑没跑完 | `GET /api/session` | 只剩 localStorage 里一个孤立 id |
| **原始 .docx 字节流** | `GET /api/session-file` | docx-preview 吃的是原始 ArrayBuffer，只有文本骨架会渲染成**空白文档区**（实测踩到 `docLen: 18`） |
| 进度与结果 | `GET /api/review-status` | 看不到进度、拿不到结果 |

**四、顺手修掉两个控制台红字来源**

1. `consumeStream()` 把 detach 的 202/200 JSON 响应当 SSE 解析，报「审阅连接意外中断」——正常情况显示成故障。改为按 `content-type` 分流。
2. `/api/session` 会话不存在返 404 → 控制台常驻红字。但「刷新后发现会话没了」是正常路径（服务重启/LRU 淘汰），改为 **200 + `exists:false`**；另补内联 SVG favicon 消掉 `/favicon.ico` 的 404。

### 6.48 模型复核从「默认关闭」改成默认开启（目标点 13）（本轮）

**问题一：复核根本没跑。** `server.mjs` 读 `body.useRecheck === true`（纯 opt-in），而**前端从来没传过这个字段** → 应用里每一次审阅都没有模型复核。修法：复核默认跟随模型审阅。

**问题二：复核跑了，但 58% 的条目其实没复核到。** 前端从来没渲染 `recheck.byKey`，补上之后坏消息才露出来：19 条问题里 **11 条是「模型未返回该条结论」**。同一份稿子、同一份代码，三次跑出 **58% / 42% / 100%** 回收率；单条单独问也只有 **47%**。

根因：推理模型随机把 **1.2—1.5 万 token 烧在推理链**上，正文 JSON **两头截断**；而 `parseJsonLoose` 的「补回被截掉的开头」兜底只处理「只截头」，头尾都截时返回 null → 整批记成 `unsure`。**`unsure` 看起来是「模型判断过但拿不准」，用户无法分辨它根本没被复核。**

三层修法：① `extractCompleteObjects()` 逐个抠出**已完整输出**的元素（未写完的直接丢弃，绝不猜）；② compact 重试（极简提示词，禁掉最费输出的 `better`）；③ 显式重试轮 + `stats.noReply` 单独计数。

**判断「有没有截断」不能只看「JSON 能不能解析」** —— 解析器的兜底会把截断掩盖成成功，必须核对**回收条数**是否覆盖全部序号。

| 方案 | 回收率 | 用时 |
| --- | --- | --- |
| 8 条/批（原值） | 11/19 = **58%** | 63s |
| 4 条/批 | 8/19 = 42%（不稳定） | 33s |
| 4 条/批 + compact 重试 + 补问 | **19/19 = 100%** | 82s |

三份稿件合计 **32/32 = 100%**（`data/verify/recheck-e2e.json`）。

**顺带浮出一个有分量的数字**：模型对规则改法的**不同意率约 36%**（22 条里 8 条），逐条看都有道理（「百吨」是量级概称不宜改「100吨」；「不但…而且…」表递进是误报；「一下子就」是正常叙述用语）。这正是目标点 13 要模型复核的原因。异议现在显示在批阅详情的「模型复核」块，`disagree` 红色、`unsure` 灰色（**不能把「无法判断」画成绿色**）。

### 6.53 修掉「改口径伪造进展」的陷阱（本轮）

改判后重跑 `--reuse`，报告显示「命中过 **18/18 = 100.0%**」—— **模型一行没改、一次没重跑**，变的只是分母（20→18）。这是最容易被当成进展的假象。


### 6.55 修掉 layout-check 的假失败（本轮）

### 6.57 CIT-003 经典著作「缺版本」：85% 的产出是误报（目标点 7）（本轮）

**漏报**：规则文本写着「须同时标明**卷次、版本**与页码」，但旧 `test` 只查「卷次 + 页码」，**完全不看版本**。632 篇里 1033 条经典著作脚注、844 条「卷+页」齐全，其中 **215 条缺版本**全部判为合规、一条没报。旁证：模型对同一篇稿件报出 15 条「经典著作缺版本」。

**误报（修漏报时暴露）**：旧页码判据 `/第\s*[0-9]+\s*页/` ① **匹配不了页码区间** —— 「第113—114页」不匹配，而区间恰是本刊规范要求的写法（`CIT-001` 明确要求一字线），**等于照规范写反被报错**；② 强制要求「第」字，而「，664页」是常见写法。实测**旧判据 192 条命中里 163 条（85%）是误报，其中 146 条由页码区间造成**。另外「第4册」≠「第4卷」。

**判据标定**：183 篇含「卷+页齐全」经典著作脚注的稿件中，**139 篇（76%）100% 带版本** —— 「××××年版」是本刊常态，故缺版本是真缺陷。但不能按单条判：115 篇含 ≥2 条此类脚注的稿件里 39 篇部分带版本，其中 **37 篇的版本从该著作首次出现就写上**，符合「首次写全、其后简写」惯例。故判据为**按著作、按文档顺序**判断「此前是否已带版本」。

**实现踩的两个坑**：① 上下文写在 `CHECKS` 循环体内 → 跨规则累加，轮到 CIT-003 时 `seen` 已含全文，真缺陷一条报不出；② 改成「独立预扫全文档」方向反了 → 变成「全文是否有过」，漏掉「首次缺、后面补」的情形。正确做法：**每条规则一份独立 ctx，按顺序在 test 之后登记**。

### 6.58 CIT-017 判据重写：探针探错了规则（目标点 7/11）（本轮）

**问题一：判据被自己的前置条件挡死。** 原式前置 `!isNarrativeNote(t)`，而该函数定义是「去书名号与括号后中文仍多于 40 字」。目标形态「毛泽东选集，人民出版社1991年版，第47页。」去掉书名号与括号后**正好 40+ 字** → **恰好被当成叙述性注释排除**。实测语料与**合成探针上均 0 命中**：不是语料没有，是判据把目标挡了。

**问题二：正则被英文著录误匹配。** 「…参见Martha Albertson Fineman, The Autonomy Myth: A Theory of Dependency…」能命中，因为「Autonomy」含**「论」**字，而 `[^“”]{0,12}` 碰不到后面的拉丁字母。实测该英文著录被匹配 **10 次**，是本规则唯一的「命中」。修法：要求整条脚注不含拉丁字母。修完探针 **5/5**，语料仍 0。

**问题三（最隐蔽）：探针探的是另一条规则。** `rule-liveness.mjs` 里 CIT-017 的探针原是 `mkDoc(['表1 各年数据','数据来源：'])` —— 那是**图表资料来源**形态，属 `CIT-031`，不是 CIT-017。旧探针让 CIT-017 看起来是活的，实际验证的是另一条判据；重写后旧探针失败（`✗ 未报出`），**却因 CIT-017 被归入「合法未触发」而计入通过** —— **探针失败被静默吞掉，比没有探针更危险**。已改为真判据形态并为 CIT-031 补探针。

**结论**：修好判据后语料命中仍为 0 —— **本语料中文书名都规范加了《》**，这是语料事实，故按 `auto-未触发` 标注。分布：`auto 88 / 未触发 3 / model 18 / manual 27 = 136`（88+3=91，与 `assert-rule-status` 口径一致）。

### 6.60 修掉「静默漏改」：归并条目只改第一处（目标点 5/13）（本轮）

`/api/apply-fixes` 把归并条目按 `occurrences` 展开，取 `o.autoFix || raw.autoFix` —— occurrence 上没有自己的 `autoFix` 时**回退到父条目**，而父条目 offset 是**首处**偏移。后果：一条「全文共 2 处」的条目勾选后只改第一处，第二处用首处偏移替换、落到别的文字上，被**静默记为「未产生变化」**：

```
applied=1 skipped=[{"reason":"未产生变化"}]   ← 应为 2 处
```

用户勾一条以为全改了，实际只改一处，**且没有任何报错**。`FMT-014` 是唯一做对的一条；现已固化为**通用不变式**：任何「既产出 autoFix、又做同类归并」的规则，每处 occurrence 都必须带自己的 offset 与 autoFix。端到端验证 5 篇「应为 N 处 → applied=N skipped=[]」，全部逐处落地。

**另一个坑**：判据最初用 `MARK.exec(t)` **只取每段第一个匹配** → 同段两处标记只报 1 处，而 `occurrences` 正是「勾一条改全文同类」的依据，**漏一处就等于那处永远改不掉**。已改为 `g` + `while(exec)`。

### 6.61 未纳入的形态（说清为什么）（本轮）

`【说明：…】`（42 种）多是编务给作者的**有效沟通内容**，不是残留；`【（中美？）】【（置？）】` 译者疑问标记实测**只有 9 次、2 种**，且同族 `（《怎么办？》）`（18 次）是**合法书名**（书名本身含问号）。样本太少、近邻易误报，**不建规则** —— 不用一条不可靠的判据换覆盖率。

### 6.62 LANG-008 口语化扩充：同时守住「刻意不报」（目标点 9/11）（本轮）

### 6.64 LANG-003 赘余扩充：挡住两类「高频正常汉语」（目标点 9/11）（本轮）

### 6.67 格式/语言引擎的同类漂移排查（目标点 7/11/12）（本轮）

第 19 轮在引文规则发现「页面标题与代码行为不符」后，本轮把同类排查推到格式与语言引擎。**结论：这两个引擎漂移风险轻得多** —— 它们的 `detect.patterns` **确实被执行**（`new RegExp(pat,'g')` 循环），声明与行为只隔一层；引文引擎的 patterns 从不执行、行为全在 CHECKS 数组，两层完全脱节。

**① FMT-020 标题比代码宽得多（真漂移）**。页面写「破折号用『——』，连接号用『—』，不得混用」，代码实际只有 `[0-9]{4}\s*[-~～]\s*[0-9]{4}`，**只查四位年份区间**，从不检查破折号。代码自己的 suggestion 里「破折号用两字线」那句是**空话**。已收窄标题为「年份区间用减号或波浪线（应用一字线「—」）」并补 `detect.method`（四类豁免上下文）。

### 6.68 markdown 残留判据的假阳性（本轮附带修正）

把「三个规则库全部字段无 markdown 残留」从格式库扩到引文库时，报出 `CIT-005.evidence[0].comment`。查原文是编辑批注里要作者填写的**空位**（`***（作者名…），“*******”（文章名…），最后访问日期：****年*月*日`），不是 markdown 强调。原判据 `/\*\*[^*]+\*\*/` 会**跨过这些空位**把两个无关的 `**` 配成一对。

**markdown 强调定界符内侧不能是空白**，且定界符不能是 `***`。据此改写判据并配 7 个用例自测（真强调/句首强调/行内代码→报出；编辑占位符/单星号/`** 重点 **`/纯文本→不报），7/7 通过。**教训与死判据同源：判据写松了会把真实数据误判成缺陷。**

### 6.69 缺口复核：先把「39% 缺口」这个数字复核一遍（目标点 6/7/11）（本轮）

`rule-gap-analysis.mjs` 长期给出「模型报的问题里 **39% 不属于规则库任何一条规则**」，但它自己的注释承认存 category/title/quote 是「才能人工判断」——**这个数字一直是未经复核的**。新增 `tools/gap-remap.mjs` 做复核：把每条缺口的 `quote` 单独喂给三个确定性扫描器，看有没有已实现规则能命中。

**我在这件事上写坏了三次探针**：① 探针只有一个段落，`FMT-001`/`FMT-036`（文档级）在任何文本上恒真（含空串、含「今天天气很好。」）→ 报出「**100% 已被覆盖**」，看着完美实为探针不合格；② 漏了 `FMT-027`，它靠**段落属性** `w:ind w:firstLineChars` 判断、且代码明确归并为每篇一条，同样恒真；③ 中性句放了「（一）」「正文。」，`CIT-002` 命中——但**那不是假警报**，探针把该文本**同时当作脚注**喂进去，「正文。」作为脚注确实违规（「探针文本」与「探针角色」是两个维度）。

**教训：排除表要按「判据是否依赖文档级属性」定，不是按「看起来像不像文档级」。** 已加 `DOC_LEVEL` 排除表 + 自检（中性文本必须零命中，否则拒绝出结论）+ 「命中位置必须落在 quote 内部」限制。

**结果**：已被现有规则覆盖 **43 条（21.9%）**（原报 0，未复核）；真缺口下界 **153 条（78.1%）**。报告明确标注这是**下界**（单句探针缺全文上下文）。

### 6.70 CIT-026 改判为人工复核：候选总体 22 处、零真违规（目标点 7/9）（本轮）

复核中发现 `CIT-026`（非引文不得加引号）在**「在“文革”前后」这种普通文本上就命中**。判据 `/[“”]/.test(t) && !/《/.test(t) && t.length < 40 && !hasPage(t)` 即「短脚注+含引号+无书名号+无页码」，等于把**所有正常加引号的脚注**都报出来。

### 6.71 FMT-024 扩充：从「编辑自己的修订」反推判据（目标点 6/7/10/11）（本轮）

上一轮列出的 153 条真缺口，本轮从「格式体例/引文与注释」入手，先做**年代表述**。原 `FMT-024` 只认「N世纪XX年代」（阿拉伯数字世纪），实测「上世纪N十年代」**17 处零覆盖**（上世纪六七十年代 5、上世纪八十年代 4、上世纪90/80/70年代 8）。

**方法要点：刊例偏好不能凭常识推断，要在修订记录里找证据。** 把 27190 组修订对里「年代写法发生形态变化」的全部捞出（67 处）+ 批注提到年代表述的（14 条），得到两条决定性证据：

> 「按理，此处该按刊例调整为 **1950—1960年代**，但是整段的几个时间段都用世纪表述，暂且不改，以达到局部统一……」

> 「……作者所述 **18世纪60年代【已由一审按刊例调整为1760年代】**……」

第一条同时给出**判据**（1950—1960年代 是目标形式）和**边界**（有时会为段内统一故意保留世纪表述）——所以严重度保持「低」、同篇归并，这条边界是编辑说的不是我推的。修订还显示编辑会把中文数字世纪改阿拉伯数字（「二十世纪」→「20世纪」36 处、「十九世纪」→「19世纪」）。判据扩成五类：N世纪XX年代 / 复合年代 / 上世纪N十年代 / 单独N十年代 / 中文数字世纪。

**三个坑**：① `convertCentury` 的 `d*10` 在 `cnNum` 扩成认「三十」→30 后变成 ×100，「二十世纪九十年代」被算成 **2800年代**（判据：`cnNum` 结果 ≥10 直接用，否则才 ×10）；② pattern 顺序让「二十世纪二三十年代」被短 pattern 先匹配成「三十年代」，把**区间**当单点（修法：长的排前面 + 后顾 `(?<![世纪])`）；③ **书名号排除是必需的**——「二十一世纪」141 处绝大多数是书名/刊名（《二十一世纪资本论》《二十一世纪》），不排除则假阳性接近 100%。

**结果**：FMT-024 命中 353→**613 处 / 136 篇**，「上世纪N十年代」覆盖 0/17→**17/17**，全部 55+ 种改写组合经人工核对算术无误；新增「N世纪」类抽查全是正常叙述行文。编辑批注的例子可原样复现（释启鹏那篇输出「改写为『1950—1960年代』形式」，与批注一字不差）。全语料 12677→**12729**，编辑批注重合 1539→**1554**。

**一条被我自己否掉的验证**：中途想证明「FMT-024 有信号」，比「有修订且涉及年代」与「无修订」稿件的命中率，结果**反了**（21.9% vs 30.2%）——探针只查「段落里是否出现过年代表述」，而 75.9% 的修订稿都出现，根本没区分「编辑改了年代写法」与「编辑改了别处、段落恰好有年代」。**测不出差异的探针，结论无效。** 换成直接找修订对里的形态变化后证据才干净。

### 6.72 Word 域代码污染解析：全语料 4278 处假阳性（目标点 7/8/11）（本轮）

查缺口清单里的「书名号嵌套误用半角尖括号」，量候选总体时先撞到更大的问题：**全语料半角尖括号 `<…>` 有 4676 处**，高频形态是 `<style>` 138、`<author>` 121、`<EndNote>` 84 —— 不是作者写的。

**根因**：OOXML 里 Word 的域由 `begin` / `w:instrText`（**指令，读者看不见**）/ `separate` / `w:t`（**缓存结果，读者看得见**）/ `end` 围成。`src/docx.js` 的 `paragraphText()` 原来把 `w:instrText` 与 `w:t` 一视同仁拼进文本，于是 EndNote / Zotero 塞进指令里的整段 XML 变成「脚注内容」。实测这类域 **140 个 / 22 篇**（`EN.CITE` 84、`ZOTERO_ITEM` 54、`CNKISM.UserStyle` 2）。注意 `scanner-format.js` L164 早有一个**只在段首**的 `CNKISM` 补丁——局部补丁治不了系统性问题。

### 6.93 校准：Δ痕迹 低不等于规则坏（本轮最重要的教训）

我先按 Δ痕迹 最低排序，头两名 FMT-036（−23.1）与 FMT-024（−14.0）看着都该删。查编辑证据后结论**相反**：

| 编辑修订方向 | 处数 |
| --- | ---: |
| 中文数字 → 阿拉伯数字（「八十年代」→「1980年代」） | **92** |
| 阿拉伯数字 → 中文数字 | **3** |

原文样例：「运史自**五、六十年代**以来」→「运史自**1950—1960年代**以来」；「**八十年代**人道主义的兴起」→「**1980年代**人道主义的兴起」；「**十九和二十世纪**的历史记忆」→「**19世纪和20世纪**的历史记忆」。**若只看 Δ痕迹 就会误删这条规则。**

| 群体 | 文件名含「一审/done/定稿…」 | 不含 |
| --- | ---: | ---: |
| 有痕迹 448 篇 | 85.9% | 14.1% |
| 无痕迹 184 篇 | 27.2% | **72.8%** |

无痕迹组绝大多数是**还没进过编辑流程的早期稿件**，本就更容易有格式问题。故 Δ痕迹 低可能只说明「这条规则抓的是编辑会在早期就改掉的格式问题」——**那正是它该做的事**。

## 七、已知边界与限制

1. **平台内容审核**：火山方舟对涉政治表述的输入有内容审核。本刊为政论性刊物，部分段落可能被拦截。智能体已实现「换模型 → 切小窗口」两级兜底，仍不通过时会在报告中列出被拦截的段落号，明确要求人工审阅，不会静默漏审。
2. **需回原始文献核对的问题**：引文页码、数据来源、经典著作版本、译名对错，规则引擎与模型都只能提示「须核对」，不能替代查证。
3. **图内文字**：图片中的文字无法用规则引擎检查；如需检查可用多模态模型（豆包 Seed 2.1 Pro）。
4. **自动修复范围**：只有标点、年代写法、约数写法等确定性规则支持一键修复；语义类问题只给建议，由编辑决定。尾注类问题目前检出的 12 条均为著录格式判断，不支持自动改写。
5. **`legacy .doc` 文件**：需先另存为 `.docx`。
6. **尾注路径覆盖度低**：全语料 632 份 `.docx` 里只有 1 份使用尾注，尾注扫描在真实语料上仅这一份得到验证，样本偏少。
